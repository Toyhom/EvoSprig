# Episode Studio 运行时与资源使用

Episode Studio 将导演、图像生成、视频渲染和 CPU 媒体工作拆分到不同服务中。一个制作会话仅加载一次模型，并在多个镜头和影片之间复用。API 导演会移除本地语言模型分配。

<a id="measured-rendering"></a>

## 实测渲染

在 H100 80 GB 硬件上，使用随附的 1.5 MP、12 步渲染配置观察得到：

| 渲染 | 实际耗时 |
| --- | ---: |
| 12 秒请求，在 1664 × 928 下输出 12.25 秒，包含初始模型加载 | 480.02 s |
| 6 秒请求，两次预热渲染 | 154.48–157.57 s |
| 5 秒请求，两次预热渲染 | 111.58–111.76 s |

这些是 ComfyUI 执行时间。一个镜头还需要首帧、导演和审核；重拍会重复相应的生成阶段。更长片段和不同设置应单独测量。

<a id="framework-overhead"></a>

## 框架开销

对一个活跃制作进行 133 秒采样，测得 EvoSprig worker 的 **RSS 为 179–295 MiB**，平均使用 **0.10 个 CPU 核**。模型服务是独立的：在该时间窗口内，视频进程使用了 70–74 GiB 主机内存和 48–54 GiB GPU 内存。本地导演在四块 GPU 上各预留约 74.7 GiB；该预留包含其服务缓存。这些是来自该部署的观察结果，可用于为类似会话估算规模。

多模态检查点在每次运行中仅存储一次大字符串。在使用生产检查点和五次连续状态变更的隔离比较中：

| 每次运行的存储 | 完整 JSON | 去重字符串 |
| --- | ---: | ---: |
| 每次保存重写检查点 | 24.08 MB | 2.89 MB |
| 保存时间中位数 | 240 ms | 91 ms |
| 五次保存后的 SQLite 数据库 | 24.13 MB | 6.91 MB |

数值使用十进制 MB。两种路径都恢复了相同状态。完整数据库包含所引用的字符串，并且仍是备份单元。

<a id="what-determines-episode-time"></a>

## 什么决定单集时间？

对于顺序镜头，制作时间大约为：

`startup + planning + reference library + Σ(first-frame attempts + video attempts + review + orchestration) + assembly`

一个确定性计时节点会根据目标时长和语音长度平衡镜头时长。在一个 24 镜头的生成草稿上，它通过原生运行时在 0.51 秒内将 130 秒调整为 180 秒，未调用模型，也未更改对话或故事事件。

启动开销每个会话仅需承担一次。复用 `series` 会跳过已有的角色和地点引用。默认团队允许每个帧和视频各尝试两次，然后在 `notes` 中继续处理剩余审核意见；使用 `build()` 更改这些限制。具有前序帧依赖的镜头按顺序运行。独立制作可以重叠进行导演、图像和视频工作；一个图像 worker 和一个 ComfyUI 实例每次各运行一个生成任务。

对于固定的片段大小、模型配置和尝试次数上限，生成工作量大致随镜头数量增长。随着单集增长，运行时会保留节点结果和事件。对于 `V` 个展开节点、`E` 个依赖项和 `P` 次调度遍历，当前调度器最多扫描 `O(P × (V + E))`。大字符串存储在 `O(U)` 空间中，用于唯一内容加状态引用；每次保存仍会遍历检查点以查找并哈希它们。视频模型的注意力和激活内存取决于潜在帧数、分辨率和所选注意力后端。

使用[部署设置](../../apps/episode-studio#deployment-settings)选择 API/本地导演、并发度和模型生命周期。使用画布的节点计时来区分高成本生成与缓慢的工具连接或重复审核。
